Rencana & rancangan · 2026-09-06 · proposal, belum ada kode · pendahulu: cmd/simbot (Go)

Menjalankan bisnis itulah lewat API-nya sendiri, dan membuktikan angkanya

Satu program memerankan pemasok, pembeli HO, staf DC, supervisor dan kasir toko, pelanggan, handheld RFID, HR, dan keuangan. Ia menggerakkan cloud (Postgres), DC edge (SQLite), dan store edge (SQLite) hanya lewat endpoint produksi, memegang model dunianya sendiri, dan menilai apakah yang sistem laporkan sama dengan yang benar-benar terjadi.

Dirancang dari kegagalan simbot lama yang dicatat audit simbot sendiri. Dokumen sumber dengan lampiran lengkap ada di repo: SIMULATION-PLAN.md.

Yang bagus darinya dibawa: kontrak passthrough jam virtual, invariant sebagai data bersaverity, korelasi per request, coverage sebagai keluaran, guard destruktif yang fail-closed, sim_result.json. 2Prinsip yang tidak bisa ditawar

  • P1Lewat API, atau tidak sama sekali. Setiap aksi manusia menjadi request ke node yang benar. Endpoint yang tidak ada menjadi baris di laporan product gap, bukan alasan menulis SQL.
  • P2Satu seed, satu cerita. Semua keacakan dari RNG yang diturunkan dari (seed, persona, hari virtual). Run yang sama dua kali menghasilkan intent log yang identik.
  • P3Tidak ada kegagalan yang ditelan. Setiap intent membawa ekspektasi: 2xx, atau penolakan spesifik. Selisih apa pun tersimpan dengan request, response, dan state dunia. Tidak ada daftar tolerate.
  • P4Dunia adalah ekspektasi, sistem adalah kenyataan. Simulator membaca sistem sebelum bertindak dan tidak pernah memasok state agar pemeriksaan lolos.
  • P5Run terisolasi. Postgres sendiri, SQLite sendiri, state run di simulator. Tidak ada flag global di tabel bisnis. Tidak pernah migrasi database yang tidak ia buat.
  • P6Nol kode simulasi di binary produksi, kecuali dua seam yang defaultnya persis perilaku produksi: Clock dan endpoint kontrol di balik INVENTORY_ENABLE_TEST_CONTROLS.
  • P7Setiap pemeriksa punya jalur gagal yang terbukti. Skenario yang tak pernah bisa merah tidak boleh masuk CI.
  • P8Satu sumber konfigurasi. Skenario adalah satu file TOML; hasil run menyimpan konfigurasi terselesaikan, seed, dan commit backend.

3.3Waktu: jam bisnis virtual, jam keamanan nyata

Dua jam, sengaja dipisah

  • Jam bisnis (Clock::now()): kapan penjualan terjadi, barang bergerak, shift dibuka, tanggal punch, masa berlaku promo, segmen member 90/180 hari, periode payroll. Ini yang dimajukan simulator.
  • Jam keamanan (tetap Utc::now()/now()): kedaluwarsa sesi, lockout login, lease device, breaker sync, retensi outbox. Kalau ikut virtual, "setahun dalam sepuluh menit" mematikan semua sesi di hari pertama dan yang diuji jadi auth, bukan bisnis.

Seam di backend (fase 0)

  1. src/clock.rs: trait Clock, SystemClock, ControlledClock; AppState.clock dan konteks edge. Default SystemClock, binary produksi tak berubah.
  2. Audit 159 Utc::now() di Rust dan ±200 now() di SQL adapter Postgres menjadi tiga kelas: metadata (biarkan), stempel bisnis (ganti), jendela bisnis di SQL (ikat parameter $now). Hari ini tak ada abstraksi jam sama sekali; helper privat fn now() di edge/till.rs:38 adalah seam termurah pertama.
  3. Gate tests/clock_authority.rs bergaya write_authority.rs: daftar file yang boleh memanggil Utc::now() beserta alasannya.
  4. POST …/control/clock di cloud dan edge, hanya bila INVENTORY_ENABLE_TEST_CONTROLS=true, pola yang sudah ada di control.rs.

3.4Sync di bawah simulasi, dan rencana chaos

Ini sifat paling penting arsitektur itulah: edge tetap beroperasi tanpa cloud. Simbot lama tak pernah mengujinya; gate 5 mereka dikapalkan tanpa rekonsiliasi cloud.

  • Quiescence: semua run_cycle melaporkan Idle, commands_applied == 0, apply_pending kosong, watermark cloud = seq terakhir edge. Invariant konvergensi hanya dinilai di titik tenang.
  • Perintah menumpang respons ingest (20 per respons). Edge tanpa fakta pun tetap mengirim batch kosong tiap siklus. command_type yang tak dikenal memblokir stream, bukan dilewati, dan muncul di GET /api/v1/sync/fleet; invariant K5 membaca ini.
  • Rencana chaos bertimestamp virtual di file skenario: partition, drop_response (pola CommitThenDropCloud yang sudah ada di test), duplicate_batch, restore_edge_from_backup, generation_rollover dalam urutan benar dan salah, printer_down, handheld_misread, terminal_decline.
  • Restore dari backup harus ditolak: ingest_batch hari ini diam-diam melewati seq <= durable, jadi skenario ini merah sampai lubang itu ditutup. Itu tujuannya, dan ia dibawa ke CI sebagai known-failing, bukan dimatikan.
  • Setelah run, GET /api/v1/inventory/time-machine/sync-divergence per origin membuktikan log fakta edge dan cloud identik; bila divergen, crate time-machine menghasilkan minimal_fixture yang bisa langsung ditempel jadi test.

3.5Identitas dan auth yang nyata

  • Node simulasi selalu berjalan dengan INVENTORY_AUTH_MODE=required. Mode disabled mengubah semantik: semua jadi ADMIN, login menjawab 409, actor_id wajib "development". Harness live hanya menoleransinya bila node milik pemilik memang begitu, dan hasil run menandainya.
  • Akun per persona dibuat admin bootstrap lewat POST /api/v1/auth/users dengan peran sebenarnya (CASHIER < SUPERVISOR < ADMIN). Kredensial edge bukan PIN endpoint: POST /api/v1/auth/edge-assignments lalu POST /api/v1/auth/edge-policies/{origin}/publish mengirim policy ke node; setelah sync, kasir login di edge.
  • Bearer menang atas cookie dan tak butuh CSRF; jalur cookie + x-csrf-token dilatih satu skenario auth khusus. Permukaan pembeli (/api/v1/member/*) hanya cookie, jadi persona Pelanggan memakai cookie jar.
  • actor_id: cloud menolak 403 bila tak sama dengan username sesi; edge menimpanya dengan username sesi. Karena tiap persona login sebagai dirinya sendiri, keduanya benar tanpa kasus khusus.
  • Handheld didaftarkan sebagai device (device_key hanya sekali) dan menandatangani observasi dengan HMAC atas kanonik POST\n/api/v1/rfid/observations\n{DEVICE_ID}\n{ts}\n{seq}\n{sha256 body}, persis scripts/rfid_simulator.py.
  • Putaran kunci supervisor ada di body: void, retur, dan payout kas membawa supervisor: {username, password}. Kasir memegang referensi ke supervisor tokonya; skenario negatif mengirim kredensial salah dan mengharapkan penolakan.
  • Matriks negatif per skenario: tiap endpoint mutasi juga dipanggil peran terendah (harap 403), tanpa sesi (401), body salah (4xx yang tepat), Idempotency-Key sama dengan body berbeda (409).
  • Dua mekanisme idempoten didukung klien: idempotency_key di body (mayoritas endpoint) dan header Idempotency-Key + If-Match: "N" pada sumber daya berversi (supplier, item, artikel, warna, vocabulary, voucher). ETag dibaca dari respons sebelumnya dan disimpan di dunia.

8Coverage endpoint

  • Denominator: tests/route_catalog.rs memindai .route("…", get(a).post(b)) di cloud/http/mod.rs, cloud/media.rs, dan edge/http.rs menjadi routes.json (node, method, pattern, role dari required_role sungguhan). Test merah bila hasil pindai berbeda dari berkas tersimpan, jadi route baru masuk katalog secara sadar.
  • Numerator: log panggilan simulator dicocokkan ke pola.
  • Laporan: persen per node dan daftar tak tersentuh per modul; entri exempt beralasan (SSE assistant, streaming media).
  • Ratchet: coverage-floor.toml menyimpan angka nyata terakhir; acceptance gagal bila turun.

10Guardrail, sebagai kode

  1. DATABASE_URL in-process harus lokal atau bernama sim_*; SIM_ALLOW_REMOTE=1 wajib untuk lainnya, dan tetap menolak host yang cocok SIM_DENY_HOSTS (default onrender.com).
  2. Simulator tak pernah menjalankan migrasi kecuali pada database yang ia buat sendiri pada run itu.
  3. Harness live menolak skenario ber-jam-virtual bila node melaporkan test controls mati.
  4. Setiap request bertanda x-sim-run, x-sim-actor, x-request-id; Idempotency-Key dicetak sekali per intent dan dipakai ulang saat retry.
  5. Tidak ada sleep di simulator; latensi fake hardware adalah waktu virtual.
  6. cargo build default tidak membangun sim; binary produksi tak pernah menautkan crate ini.

11Rencana fase

Ukuran: S ≈ 1–2 hari kerja satu sesi, M ≈ 3–5, L ≈ 1–2 minggu. Fase 0 dan 1 bisa dikerjakan paralel oleh sesi berbeda kecuali yang ditandai.

  1. 0

    Seam di backend M · tiga lane paralel

    • 0a Jam: src/clock.rs; AppState.clock dan konteks edge; audit ke tabel kelas A/B/C di docs/clock-audit.md; kelas B/C diganti; tests/clock_authority.rs; endpoint control/clock di cloud dan edge.
    • 0b Harness bersama: inventory_backend::harness di balik feature harness: Fleet, IngestOverHttp, sync_until_quiescent, pembuat DB per run; tiga test yang menyalinnya beralih memakainya.
    • 0c Katalog route dan gate merah: tests/route_catalog.rs; daftarkan 0028 di edge/sqlite.rs; allowlist blok migrasi yang sengaja dilompati di migration_hygiene.rs; .github/workflows/ci.yml pertama repo.

    Exit: cargo test hijau dengan jam tersuntik; test baru memajukan ControlledClock 90 hari mengubah segmen member tanpa mematikan sesi; CI pertama hijau.

  2. 1

    Inti dan smoke M–L · setelah 0a/0b

    • crates/sim: scenario, world, clock, node, harness, fakes, record, runner invariant dengan S1, S2, S4, S9, K1, K2, E1, E2.
    • Persona rantai barang: Pembeli, DC, Merchandiser, Penanda, Alokator, Picker/Packer/Dispatcher, Supervisor toko, Kasir, Pelanggan. Ini port full_chain_integration.rs ke bentuk persona.
    • CLI run, sim_result.json, intents.jsonl, failures/.

    Exit: sim run --scenario smoke hijau di bawah 2 menit; mutation check merah; dua run dengan seed sama menghasilkan intents.jsonl identik.

  3. 2

    Acceptance bisnis L · paralel per domain

    • Persona lengkap: Komersial, Keuangan, HR, Auditor, Pemasok fake dengan pengiriman sebagian dan terlambat, matriks negatif per peran.
    • Profil permintaan; acceptance 30 hari; katalog invariant penuh; coverage dan floor; known-failing.
    • CI: PR menjalankan smoke; nightly menjalankan acceptance dengan floor ratchet.

    Exit: acceptance hijau; angka coverage nyata tercatat; daftar product gap pertama, misalnya transfer antar toko.

  4. 3

    Waktu dan gangguan M–L

    • soak 12 bulan: payroll, tutup periode, promo lintas bulan, segmen member.
    • chaos: partisi, drop response, duplikasi, restore dari backup (menutup lubang seq <= durable), rollover generation, printer mati, misread.
    • load live di rig tiga proses; demo live untuk mengisi DB demo lewat API.

    Exit: soak hijau dengan pemeriksaan bulanan; setiap item chaos punya skenario dan status.

  5. 4

    Kendali dan UI M

    • sim serve: API dan SSE; replay dengan laporan drift; jembatan time-machine (sync-divergence, what-if, fixture otomatis).
    • Modul hub Simulation.

    Exit: run dimulai dari hub, diikuti langsung, hasil diunduh; satu divergensi buatan menghasilkan fixture yang lolos is_faithful.
