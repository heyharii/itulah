# The Gudang in the cloud — one DC, two places to run it

Written 2026-10-04. The distribution centre stops being a *required* second
node. Its operations can run **inside the cloud process** against the cloud
ledger, and the standalone `dc` **server** keeps working unchanged for a
warehouse whose readers and printer need a local node. Which of the two hosts
the Gudang is a per-deployment choice, not a fork: one code path, one contract,
one ownership model that already knows how to hand authority between them.

Everything below was read before it was written: `backend/src/bin/{cloud,dc,
store}.rs`, `backend/src/edge/http.rs` (the `/api/v1/dc/*` routes),
`backend/src/cloud/http/mod.rs`, `backend/src/cloud/postgres/{queries,sync,
suppliers,payables,letters,auth_policy,allotments}.rs`,
`deploy/README.md`, `deploy/edge/` (`dc.env.example`, `dc-edge.service`,
`nftables-dc.conf`), `deploy/scripts/provision-dc.sh`,
`deploy/gcp/startup-demo.sh`, `deploy/frontend/gen.mjs`,
`frontend-hub/src/lib/api.ts`, `frontend-hub/src/lib/edge-session.tsx`,
`CONTEXT.md`.

## Implementation, 4 Oct 2026 (owner: "ga ada lagi server dc sementara")

Built as **the same node, hosted**, rather than a second set of DC rules — so
Phase 1's drift risk does not exist:

- `backend/src/edge/db.rs` — the node's database handle with rusqlite's shape
  and two backends: its SQLite file (unchanged for shops and DC servers) or a
  Postgres schema. SQLite spellings are translated (`?N`, `INSERT OR IGNORE`,
  scalar `MAX(a,b)`, `a IS b`, `json_each`); every statement inside a
  transaction runs under a savepoint so a failed statement undoes itself
  alone, as in SQLite; constraint errors keep SQLite's wording.
- `backend/migrations/edge_postgres/0001_edge_schema.sql` — the whole node
  schema (119 tables, 21 guard triggers as PL/pgSQL, 65 foreign keys),
  generated by `backend/scripts/edge-schema-to-postgres.py`. A later SQLite
  migration gets a Postgres twin in `EDGE_POSTGRES_MIGRATIONS`.
- `backend/src/edge/hosted.rs` — `INVENTORY_DC_HOSTING=cloud`: the cloud
  process opens the node in schema `dc_edge` of its own database, registers
  its origin (`ensure_hosted_dc_origin`), syncs over loopback with the same
  protocol, and serves its router under `/edge`. `DC_IMPORT_SQLITE` moves a DC
  server's file in once (same generation, same watermarks).
- Sandbox (`cloud/tenancy`): each business gets its own hosted Gudang at its
  head-office site, in its own database; sync names the business
  (`x-itulah-business`).
- Printing: `bridge:<name>` printer addresses go through
  `edge/print_bridge.rs`; `scripts/print-bridge-cloud.py` in the warehouse
  long-polls the cloud and feeds the LAN/USB printer (`PRINT_BRIDGE_KEY`).
- Deploy: `deploy/gcp/startup-demo.sh` switches on VM metadata
  `itulah-dc-hosting=cloud` (no `dc` container; Caddy `/edge` → cloud).

The DC server mode is unchanged and still available.

## 0. Rulings

| Question | Ruling |
|---|---|
| What does "merge" mean? | The cloud process serves the DC operational surface (`/api/v1/dc/*`) natively, writing the Gudang's pools in its own Postgres ledger. The `dc` binary, `dc-edge.service` and `provision-dc.sh` are **not** deleted — that is the server hosting. |
| Where does authority sit? | Where it already sits. Cloud-native `dc.*` pools are `CLOUD_LEDGER` / `CLOUD_WRITABLE` rows (`postgres/queries.rs` fleet-pools). A server DC's facts keep shadowing the cloud's rows **per pool** via `pool_id_for_site` (`postgres/sync.rs:5853`) and `SHADOWED_READ_ONLY`. No new sync semantics are invented. |
| Can both be live at once? | **No — at most one writer per site.** Registering a DC origin while the cloud hosts that site's DC (or flipping hosting while an edge DC origin is active) is refused. Mixed *reading* is fine and already works; split-brain writing is not. |
| Who chooses? | An explicit `INVENTORY_DC_HOSTING=cloud\|edge` on the cloud node. Default `edge` — every existing fleet keeps behaving exactly as today. `cloud` is opt-in. |
| Sessions? | Cloud-hosted DC routes are gated by the **cloud session** and the caller's unit reach. The edge's SSO relay (`/api/v1/auth/sso/exchange`, `edge/http.rs:205`) stays for server mode and is simply not used in cloud mode. |
| Hardware? | Readers and the label printer are the honest reason a DC stays a server (`provision-dc.sh`: portals and a Printronix on the warehouse LAN). Cloud mode serves every screen and accepts RFID evidence from a tailnet-reachable reader, but **local printing is not served** — the printer routes answer an explicit "this site's DC is hosted in the cloud" refusal. Do not put a print-heavy warehouse on cloud mode. |
| Vocabulary | Product surfaces keep **Gudang** (CONTEXT.md bans DC as a unit). `dc` survives only where it already lives: the bin name, `INVENTORY_NODE_ROLE=DC`, `node_role='DC'` on a credential row. |
| Stores? | Untouched. A store is always an edge node; this plan is only about the Gudang's node. |

## 1. What already exists — the merge is smaller than it looks

- **One runtime, two names.** `bin/dc.rs` is the same program as `bin/store.rs`
  with `EdgeRole::Dc`; the role is the only difference. There is no separate DC
  codebase to merge — only a hosting decision to add.
- **Cloud-native DC pools already exist.** The `dc.receiving`, `dc.warehouse`,
  `dc.reject` and outbound-stage pools are seeded in Postgres
  (`migrations/postgres/0002_demo_seed.sql`, `0353_the_warehouse_site_is_
  kind_head_office.sql`), and `fleet-pools` already renders them as
  `CLOUD_LEDGER` rows with a shadowing rule for edge facts
  (`postgres/queries.rs` ~1740–1860): a cloud row is shadowed only where the
  edge has a row for that exact pool, respelled by `pool_id_for_site`
  (`dc.warehouse` ↔ `dc-01.warehouse`).
- **Allotment math already unions both ledgers** — `cloud_ledger_balance` and
  `edge_ledger_balance` side by side (`postgres/allotments.rs:1821`). Picking
  from a cloud-hosted Gudang needs no change there.
- **The hub tolerates no DC node.** `deploy/frontend/gen.mjs` makes the
  `/edge` rewrite conditional on `DC_URL` (line 29). What is missing is the
  Operations module's *runtime* ability to talk to the hub's own origin
  instead (`lib/api.ts:34` pins `EDGE_BASE=/edge`, with edge-only sessions in
  `lib/edge-session.tsx`).
- **The procurement brains are already on the cloud**: purchase orders, price
  amendments, article setups, letters, unbilled-receipt valuation — all written
  to read DC receipts that arrive as facts. That consumption contract is what
  native receipts must satisfy.

## 2. The gap

1. **No `/api/v1/dc/*` on the cloud.** The whole surface — intake, goods
   receipts, official counts, picklists, picks, packs, koli, packing boxes,
   shipments, dispatch trips, inbound store returns, inspections,
   purchase returns, tagging — is mounted only in `edge/http.rs:110–299`.
2. **Two state machines risk.** The edge handlers validate and transition
   against SQLite. Naively rewriting them for Postgres duplicates every
   lifecycle rule and guarantees drift.
3. **DC-resolver blind spots.** Six cloud queries assume a DC is a
   `sync_origin_credential` row with `node_role='DC'`: supplier delivery
   destinations (`suppliers.rs:3938`), unbilled receipts' warehouse join
   (`payables.rs:2028`), goods-receipt letters (`letters.rs:456,708`), outbound
   rollups (`queries.rs:1493,1843`), and the auth-policy DC count
   (`auth_policy.rs:1196`). A cloud-hosted DC appears in none of them.
4. **Native receipts vs facts.** Letters and payables read receipt records fed
   by ingest. Cloud-hosted receipts are written natively; the consumers must
   see one shape, not two, or the unbilled loop double-counts.
5. **Hub Operations is hard-wired to `/edge` + edge sessions** (`EDGE_KEY_PREFIX`
   cache namespace, `useEdgeActor`).
6. **Deployment shape.** The demo runs three containers (`cloud`, `dc`,
   `store` — `startup-demo.sh`); Caddy proxies `/edge`; seed-demo grants
   `candra`/`yudi` at origin `dc`.

## 3. Phases

### Phase 1 — Shared DC flow core
Extract the lifecycle rules from `edge`'s DC handlers (receipt open/verify/
accept, count submit, pick/pack/koli/seal/dispatch transitions, inspection,
tagging confirmation) into a module both hosts call — pure decisions, no
storage. The edge keeps its SQLite adapters; the cloud writes Postgres
adapters in Phase 2. Contract tests run the same scenarios against both.

*Why not skip it:* a second state machine that drifts from the first is the
one defect this plan must never ship; the goods flow docs
(`docs/goods-flow-build-2026-10.md`, `docs/design-rules-goods-flow.md`) are the
specification the core encodes.

### Phase 2 — Cloud-native DC API
`cloud/http/dc.rs` + `cloud/postgres/dc_*.rs` mount the same `/api/v1/dc/*`
routes, active when `INVENTORY_DC_HOSTING=cloud`. Writes go through the
cloud's existing movement writers into `dc.*` pools; receipts are written into
the **same internal shape** the fact-fed consumers read today (Phase 3 proves
which tables those are; if facts land in distinct fact tables, native writes
land in the canonical tables and the fact path becomes the fallback reader —
decided by reading `postgres/letters.rs` and `payables.rs` before coding).
Guard: startup refuses `cloud` hosting while a DC origin credential is
inventory-enabled, and origin registration refuses role DC while hosting is
`cloud` — the one-writer rule, enforced on both doors.

### Phase 3 — The resolver sweep
Replace the six `node_role='DC'` scans with one resolver: *edge DC origins ∪
the cloud-hosted Gudang site*. Each call site keeps its semantics
(destinations list the Gudang; rollups add outbound stages from cloud-native
leaves; auth policy counts one DC either way). This phase is where a
cloud-hosted DC becomes a first-class citizen of procurement, payables and
letters.

### Phase 4 — Hub Operations, same-origin mode
The Operations module picks its base at runtime from the hub's own
`/api/v1/health` capability (e.g. `"dc.hosting": "cloud"`): cloud-hosted → the
hub's own `/api` and the ordinary cloud session; server-hosted → `/edge` and
the edge-session machinery exactly as today. The `EDGE_KEY_PREFIX` cache sweep
stays for server mode and becomes a no-op in cloud mode. No screen redesign —
only the Node base and the actor source differ.

### Phase 5 — Hardware surface, stated honestly
RFID: a reader that can reach the cloud over the tailnet posts evidence as it
does to an edge node; observations file against `dc.*` pools. Printing: the
koli-label and print-session routes answer an explicit
`dc_hosting_unsupported` error in cloud mode. This is a documented limit, not
a bug: a warehouse that prints at the bench runs a server DC.

### Phase 6 — Deployment
- Demo (`startup-demo.sh`): `cloud` + `store` containers; `APP_BIN=dc` gone;
  Caddyfile loses `/edge`; `seed-demo.sh` grants `candra`/`yudi` on the cloud
  instead of origin `dc`; `register-demo-origins.sh` registers `store-01`
  only.
- Server mode: `dc.env.example`, `dc-edge.service`, `nftables-dc.conf`,
  `provision-dc.sh`, headscale `tag:dc` — unchanged, and the README says so:
  *"The Gudang runs in the cloud by default; a warehouse with local readers
  and a printer runs `deploy/edge/dc-edge.service` instead."*
- `deploy/README.md` topologies rewritten around the choice; `cloud.env.
  example` documents `INVENTORY_DC_HOSTING`.

### Phase 7 — Cut-over recipe for an existing pilot
No forced migration. A fleet running `dc-01` as an edge node keeps running it;
facts keep shadowing the cloud rows per pool. To move a site to cloud hosting:
drain unacknowledged facts → retire/suspend the origin → set
`INVENTORY_DC_HOSTING=cloud` → restart. Historical generation watermarks stay
as history; if the server comes back, hosting flips back and shadowing
restores authority to facts — both directions are the existing model doing its
job.

### Phase 8 — Verification
- **Integration** (`make test-integration` family): every `/api/v1/dc/*`
  route exercised against both hostings; the one-writer guards (origin
  registration refused under cloud hosting, startup refused with a live DC
  origin); native receipts visible to letters, unbilled and destinations
  exactly once.
- **Mixed-mode E2E**: cloud-hosted Gudang + edge store — PO raised → received
  at the cloud DC → allotment picked/packed/dispatched → `store-01` receives
  its inbound. This is the pairing every real fleet will run.
- **Shadowing regression**: start an edge DC against a site whose pools have
  cloud rows → per-pool `SHADOWED_READ_ONLY`, fleet totals do not double.
- **Hub walkthrough** through Portless + agent-browser: Operations intake,
  receiving, picking, packing, despatch against the cloud-hosted DC in one
  session, then the same screens against a server DC (relay still works).
- Preserve snapshots, server log and exact URL on any failure per repo rules.

## 4. Risks

| Risk | Mitigation |
|---|---|
| Two persistence adapters drift | Phase 1's shared core; contract tests run identical scenarios against both hosts. |
| Receipts counted twice (native + fact reader) | Phase 2 decides the canonical shape by reading `letters.rs`/`payables.rs` first; Phase 8 asserts "exactly once". |
| Split-brain writes to one site | One-writer rule enforced at startup and at origin registration (both doors, Phase 2). |
| Cloud mode oversold to hardware-heavy warehouses | Printing refusal is explicit, not a hang or silent drop; deploy README states the limit. |
| Hub cache leaks across hostings | Cloud mode never touches `EDGE_KEY_PREFIX`; existing sign-out sweep tests keep guarding server mode. |
| Rollback after cut-over | Hosting flips back; shadowing restores fact authority; no data rewrite in either direction. |

## 5. Non-goals

- No store-node changes; no new sync protocol; no schema redesign beyond what
  the hosting flag needs; no new screens; `frontend-cloud` retirement and the
  store-server plan proceed on their own tracks.
