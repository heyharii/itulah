Purchase Order → Tagging

Peta implementasi aktual: siapa mengisi apa, endpoint yang dipanggil, data dan status yang lahir, perpindahan stok Cloud↔DC, bukti pengujian, serta gap yang perlu diketahui sebelum dianggap production-complete.

120 → 118 unitContoh test: order 120, diterima/tagged 118, outstanding 2.
Bukan lifecycle approvalPO langsung ISSUED; tidak ada draft/submit/approve endpoint.

Kesimpulan eksekutif

Alur operasionalnya utuh untuk kuantitas yang diterima: PO di Cloud dikirim ke DC, barang dihitung dan diverifikasi, diidentifikasi menjadi SKU, diberi EPC, lalu masuk warehouse sebagai unit terlacak.

Verdict: berhasil, dengan batasan.

Test E2E membuat PO 120 unit, menerima 118, dan men-tag seluruh 118 menjadi EPC unik. Jadi “PO hingga tagging” berhasil untuk barang yang accepted—tetapi PO contoh belum fully received/closed karena masih outstanding 2 unit.

Alur bisnis aktual

  • Supervisor membuat PO; sistem langsung menyimpan header ISSUED dan mengirim command ke DC tujuan.
  • Receiver membuka GRN; checker melakukan blind count; verifier kedua memilih Accept atau Recount.
  • Accept menciptakan stock pending.unidentified dan receipt fact yang dibaca Head Office.
  • Merchandiser membuat article setup dengan colour/size/quantity; total variant wajib sama persis dengan kuantitas accepted.
  • Issue setup membuat article/SKU, alokasi serial EPC, tagging job, dan command ke DC.
  • Operator mencetak/memasang label lalu confirm; stock berubah menjadi unit per-EPC di warehouse dan Cloud menerima status TAGGED.

Yang tidak terjadi

  • Tidak ada endpoint update, submit, atau approve PO.
  • Tidak ada endpoint close goods receipt; GRN tetap OPEN.
  • Full receipt tidak otomatis menutup PO; hanya close-short yang bisa menutup line/header sesuai kondisi.
  • Cloud tidak punya endpoint langsung create/complete tagging job: create adalah efek issue setup, complete dilakukan DC.
  • E2E test mematikan auth dan memanggil worker sync secara langsung, bukan tiga proses/socket sungguhan.

1Supervisor membuat PO di CloudOrder langsung aktif, bukan draft.›

Diisi user

Nomor PO, supplier, DC tujuan, currency, notes, creator, lines; tiap line berisi supplier article, nama, division, tags, qty, unit price, promised date.

Proses & hasil

Insert purchase_order, line, tags; status ISSUED; response memberi purchase_order_id dan command ID.

Bisa gagal jika

DC tak punya credential owner, line kosong/duplikat, qty ≤ 0, tag/division asing, nomor PO duplikat, harga/amount invalid.

Input sistem

Proses & hasil

Bisa gagal jika

Node bukan DC, destination site tidak cocok, payload/domain invalid.

Bisa gagal jika

Supplier/actor/key tidak valid. Tidak ada endpoint aktif untuk menutup GRN.

4Checker melakukan blind countExpected quantity disembunyikan dari checker.›

Diisi checker

receipt_id, po_line_id, counted_quantity, actor dan idempotency key.

Proses & hasil

Membuat receiving_count berstatus AWAITING_VERIFICATION. Belum ada movement, stock, atau receipt fact.

Bisa gagal jika

Qty ≤ 0, PO line/receipt tidak dikenal, receipt bukan OPEN, atau key dipakai untuk payload berbeda.

5Verifier kedua memutuskanAccept menciptakan stock; Recount tidak.›

Diisi verifier

count_id, actor verifier, decision Accept/Recount, optional note, optional invoiced price, idempotency key.

Proses & hasil

Recount → RECOUNT_REQUESTED. Accept → ACCEPTED, receipt line, movement group, stock pending.unidentified.

Bisa gagal jika

Verifier sama dengan checker, recount tanpa note, count telah diputus, price negatif. Selisih harga dicatat tetapi tidak menahan barang.

6Accepted receipt naik ke CloudEdge fact → PostgreSQL read model.›

Input sistem

goods_receipt.line fact: GRN, line, PO line, quantity, counter, verifier, movement group.

Proses & hasil

Cloud upsert header/line; PO detail menghitung received, outstanding, payable dari goods_receipt_line.

Bisa gagal jika

Fact malformed atau checker=verifier melanggar check database. Pada test: received 118, outstanding 2.

7Merchandiser membuat Article SetupMengubah barang anonymous menjadi rancangan article/SKU.›

Diisi user

Receipt line, optional internal article code, name, division, tags, image, currency, colours, variants: colour + size + qty + base price.

Proses & hasil

Session OPEN. Preset supplier code/tags dari PO tersedia untuk traceability; supplier code bukan internal article code.

Bisa gagal jika

Total variant ≠ accepted qty, >5.000 unit, >10 colourways, receipt sudah disetup, vocabulary/article/size invalid, duplicate variant.

8Merchandiser meng-issue setupTitik tagging job dan EPC benar-benar dibuat.›

Diisi user

Path setup_id dan body issued_by.

Proses & hasil

Dalam satu transaksi: create/reuse article, tags, colours, SKU; lock serial counter; allocate EPC; create job/lines/command; setup OPEN → ISSUED.

Bisa gagal jika

Session bukan OPEN, destination DC tak lagi terdaftar, atau constraint article/SKU/EPC gagal.

9Tag command diterapkan di DCExact receipt pile wajib masih tersedia.›

Input sistem

tagging.job.activate: receipt line, article, SKU lines, prices, QR/barcode dan daftar finished EPC.

Proses & hasil

Stock exact receipt berpindah melalui Identification menjadi per-SKU quantity di pending.untagged; print queue tersimpan.

Bisa gagal jika

Site salah, pile hilang, balance tak sama, EPC duplicate/tidak cocok SKU, total job tidak sama dengan delivery.

10Operator mencetak dan memasang tagQueue memuat label siap cetak.›

Dibaca operator

SKU, quantity, QR, barcode, dan finished EPC strings dari GET /dc/tagging-jobs.

Aksi fisik

Cetak label, pasang label yang sesuai ke unit, cek jumlah fisik sebelum confirm.

Risiko operasional

Aplikasi sudah memint EPC di Cloud; salah-tempel label adalah kontrol proses fisik, bukan validasi software di endpoint confirm.

11Operator mengonfirmasi taggingQuantity subjects menjadi unit subjects per EPC.›

Diisi user

job_id, actor_id, idempotency_key.

Proses & hasil

Setiap EPC menjadi UNIT subject dan masuk warehouse; local job TAGGED; movement facts + completion fact masuk outbox.

Bisa gagal jika

Job unknown/bukan OPEN/no lines/EPC count mismatch. Retry key sama aman; key baru untuk job yang sudah selesai ditolak.

12Cloud mempublikasikan hasil akhirTagging selesai; settlement PO tetap jalur terpisah.›

Input sistem

tagging.completed dan inventory movement facts dari Edge.

Proses & hasil

Cloud job/setup ISSUED → TAGGED; EPC muncul sebagai inventory position; duplicate completion ditoleransi.

Sisa proses

PO contoh tetap ISSUED, 118/120. Sisa 2 dapat diterima kemudian atau line di-close-short; close-short tidak masuk happy-path E2E yang sama.

Arsitektur software aktual

Control plane ada di PostgreSQL Cloud; operasi receiving/tagging berjalan offline-capable di SQLite Edge; command mengalir turun dan fact mengalir naik.

Cloud API / control plane

Endpoint PO dan article setup. Auth opsional; mutation non-sales minimal SUPERVISOR ketika aktif.

Command lane ↓

purchase.order.activate membawa order; tagging.job.activate membawa exact SKU, quantity, label, dan EPC ke satu DC.

DC API / execution plane

Receiving segregation, blind count, verification, print/attach, confirmation, movement dan idempotency berlangsung lokal.

Fact lane ↑

goods_receipt.line, inventory movements dan tagging.completed mematerialisasikan hasil Edge kembali di Cloud.

Inventory identity progression

QUANTITY@pending.unidentified → QUANTITY@pending.untagged → UNIT(EPC)@warehouse.

Status lifecycle

Purchase Order

ISSUED → CLOSED*

*Bukan karena full receipt otomatis. Header ditutup hanya saat close-short membuat tak ada line OPEN. CANCELLED diizinkan schema tetapi flow endpoint tidak ditemukan.

Goods Receipt

OPEN

Schema mengizinkan CLOSED, tetapi implementasi aktif untuk transisinya tidak ditemukan.

Receiving Count

AWAITING → ACCEPTED

Cabang alternatif: AWAITING_VERIFICATION → RECOUNT_REQUESTED, lalu checker menghitung ulang melalui count baru.

Setup & Tagging Job

OPEN → ISSUED → TAGGED

OPEN di Cloud setup; issue membuat job/command; confirmation DC dan completion fact menutup job/setup.

Apa yang belum dibuktikan oleh test ini

  • Auth-enabled flow: bearer/session cookie, CSRF dan role gates dimatikan pada E2E utama.
  • Tiga service/socket dan periodic workers sungguhan; test memakai Axum router tetapi memanggil worker sync/apply langsung agar deterministik.

  • PO 120 tidak fully received: test hanya menerima/tagging 118. Final PO tetap outstanding 2 dan secara perilaku masih ISSUED.
  • Atomic rollback bila command issuance gagal setelah PO ter-commit belum memiliki test khusus.

Gap, risiko, dan rekomendasi

Temuan dipisahkan dari happy path agar diagram tidak memberi kesan lebih matang daripada implementasi aktual.

Create PO dan issue command tidak benar-benar atomik
